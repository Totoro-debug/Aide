# Defer Tool Schema Exposure within Each Agent Run

Delay the exposure of complete Tool schemas to the model while retaining the MCP connection, discovery, and immutable generation Snapshot lifecycle defined by [ADR-0020](0020-expose-configured-mcp-tools-through-tool-gateway.md). Foreground chat and User Schedule Agent Runs initially expose `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, `exec`, and `tool_search`. Searching the existing Tool Catalog activates matching Tools for exposure in subsequent model requests. This reduces the schemas carried by requests without introducing connection or discovery work into Tool Search. Dream is not an Agent Run and exposes only `edit_file` in its one-shot request under [ADR-0024](0024-use-one-shot-dream-model-request.md).

Tool Activation belongs to one Agent Run and expires when that run ends. Each later run begins from its baseline, including a later input in the same Conversation Session. Concurrent runs use independent Agent Run Gateway views over the Runtime Generation Tool Catalog and may share reusable Tool instances without sharing activation state. Session history does not restore activation. This prevents schema accumulation across a long conversation and avoids coupling foreground and Schedule selections through shared generation resources.

Exposure is a model-context choice, not an execution gate. A model call to an unexposed Tool follows the existing Gateway lookup, preparation, confirmation, and execution pipeline whenever that Tool exists in the run's available Catalog. There is no additional activation check or special handling for calls inferred from history or emitted alongside `tool_search`. Built-in preparation retains local parameter validation; MCP preparation retains its existing complete argument forwarding. Direct invocation does not itself introduce an activation mechanism.

The available Catalog for a User Schedule Agent Run excludes the entire Built-in `ScheduleTool`, so search, schema exposure, and direct name lookup cannot reach it. This intentionally replaces the earlier rule that refused only Schedule creation while allowing listing and removal from scheduled execution. Foreground chat retains `ScheduleTool` as a deferred capability.

Tool Search uses BM25 keyword retrieval with an inverted index over deferred capabilities. Search candidates are the current Agent Run's available Tools minus the initial eight exposed Tools and any Tools already exposed through search in that run. A successfully returned Tool therefore leaves that run's later search candidates. The `tool_search` description instructs the calling model to provide English query keywords. Search returns and activates at most three matching Tools, with this limit fixed in code and absent from the Tool's parameters. Its result contains only the model-facing Tool name list, without descriptions, provenance, activation metadata, or complete schemas; schemas enter subsequent model requests through the ordinary `tools` argument.

Built-in Tool Search Keywords are English constants declared in code. MCP keywords are stored under `[mcp.servers.<mcp_name>.tool_keywords]`, mapping original remote Tool names to English keyword lists. At startup, each discovered MCP Tool uses configured keywords when present and nonempty; missing or empty keywords trigger a model call through the existing `chat` route, including its ordinary fallback to `default`, to generate English keywords for that Tool. Successful generated keywords are written back atomically to that configuration table for future startup reuse. Writeback uses the shared `.config.toml.lock` from before its latest-file reread through publication, preserves comments and unrelated configuration, and retains a user-supplied nonempty keyword entry committed by an earlier cooperating Omni writer. An ordinary external editor does not acquire this lock and therefore must not save during a Omni configuration write transaction. Generation failure uses only the original MCP Tool name as the in-memory fallback, without extracting description words or persisting that fallback. A later process startup can therefore try generation again instead of mistaking the fallback for completed keywords. If lock acquisition or writeback fails after successful generation, the Agent continues using the in-memory keywords and emits no terminal notification about that failure.

Tool Activation changes the Model Request Context revision. Before the next ReAct request, the projected token budget is therefore checked again under [ADR-0023](0023-manage-agent-run-context-by-projected-token-budget.md). There is no schema truncation or automatic eviction introduced to make an activation fit the context window.

Requirements: [BM25 Tool Search and per-run schema exposure](https://github.com/Totoro-debug/OmniAgent/issues/225).
